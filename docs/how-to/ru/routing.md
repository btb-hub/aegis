# Как метка на алерте выбирает команду.

Правило маршрутизации — это одно совпадение: **этот ключ метки равен этому
значению → инцидент уходит в эту команду**. Правило создают на **рабочей области**
проекта, не на команде. Если ни одно правило не совпало, алерт остаётся в **Алертах** и не
становится инцидентом.

[Куда нажимать](#where) | [Поля формы](#form) | [Пример: Платформа](#ex1) | [Пример: два проекта](#ex2) | [Пример: сначала NOC](#ex3) | [Пример: общая команда](#ex4) | [Как прочитать метки](#read)

<a id="where"></a>

## 01 · Где создать правило

1. **Откройте рабочую область, не Команды**
   В сайдбаре **Рабочие области** → **Platform** (или ваш проект). Блок
   **Правила маршрутизации** → **Добавить правило**. Сохранение — **Сохранить правило**.

2. **Одно правило = одно совпадение**
   В форме один **Ключ метки** и одно **Значение метки**. Два условия на одном
   правиле (И) в интерфейсе нельзя. Лишние метки на алерте не мешают — правило не обязано
   перечислять их все.

<a id="form"></a>

## 02 · Что значит каждое поле

| Поле | Что указать |
| --- | --- |
| **Разрешить команду из другой области** | Выключено, если целевая команда в этой же области. Включайте только для общей команды<br>(например DevOps в другой области). Тогда в **Целевая команда** появятся чужие команды. |
| **Целевая команда** | Кто станет владельцем инцидента. Обычно L2 или NOC. Не L3 — L3 получает работу по<br>[пути эскалации](paths.md), не из маршрутизации. |
| **Ключ метки** | Точное имя метки из мониторинга. Часто `team`, `project`,<br>`service`. Регистр важен. |
| **Значение метки** | Точное значение. `platform` не совпадёт с `Platform` или<br>`platform-prod`. |
| **Приоритет** | Целое число. По умолчанию `100`. **Большее число проверяется первым**,<br>если два правила подошли к одному алерту. При равном приоритете не полагайтесь на порядок —<br>задайте разные числа. |

> **Сопоставление глобальное**
>
> Aegis смотрит правила всех рабочих областей вместе. Правило с высоким приоритетом в Data
> может перехватить алерт Platform, если метки те же. Делайте матчер узким
> (`team=…` или `project=…`), а не голый `severity=critical`,
> если не хотите все critical в одну команду.

<a id="ex1"></a>

## 03 · Пример 1 — одно правило для Platform

Grafana шлёт `alertname=HighCPU`, `team=platform`,
`severity=warning`. Владелец — Platform L2.

Рабочая область **Platform** → **Добавить правило**:

#### Добавить правило · область **Platform**

| Поле | Значение |
|-------|-------|
| Разрешить команду из другой области | Выкл. |
| Целевая команда | Platform L2 |
| Ключ метки | `team` |
| Значение метки | `platform` |
| Приоритет | `100` |

`team=platform` достаточно. `alertname` и
`severity` можно не дублировать. После **Сохранить правило** в таблице:
совпадение `team=platform`, команда Platform L2, приоритет 100.

<a id="ex2"></a>

## 04 · Пример 2 — Platform и Data рядом

Один Grafana, два проекта. Метка `project=platform` или
`project=data`.

#### Правило A · область **Platform**

| Поле | Значение |
|-------|-------|
| Целевая команда | Platform L2 |
| Ключ метки | `project` |
| Значение метки | `platform` |
| Приоритет | `100` |

#### Правило B · область **Data** (создайте его на странице Data)

| Поле | Значение |
|-------|-------|
| Целевая команда | Data L2 |
| Ключ метки | `project` |
| Значение метки | `data` |
| Приоритет | `100` |

Одинаковый приоритет нормален: одно значение `project` не совпадёт с
обоими правилами сразу. Не кладите оба правила на Platform, если Data L2 не цель из другой
области.

<a id="ex3"></a>

## 05 · Пример 3 — critical в NOC, остальное в L2

Команды Platform NOC и Platform L2. Critical сначала на NOC, остальные с
`team=platform` — на L2.

#### Правило A · выше приоритет · область **Platform**

| Поле | Значение |
|-------|-------|
| Целевая команда | Platform NOC |
| Ключ метки | `severity` |
| Значение метки | `critical` |
| Приоритет | `200` |

#### Правило B · остальное · область **Platform**

| Поле | Значение |
|-------|-------|
| Целевая команда | Platform L2 |
| Ключ метки | `team` |
| Значение метки | `platform` |
| Приоритет | `100` |

Алерт `team=platform` + `severity=critical` подходит обоим.
Сначала `200` → NOC. Warning только с `team=platform` → L2.
Правило A также поймает critical из Data, если там та же метка. Для жёсткого разделения
лучше своя метка в Grafana, например `team=platform-noc`.

<a id="ex4"></a>

## 06 · Пример 4 — команда в другой области

DevOps живёт в области **Ops**. Алерты приходят в Grafana как
`team=devops`, правило создаёте на Platform.

#### Добавить правило · область **Platform**

| Поле | Значение |
|-------|-------|
| Разрешить команду из другой области | Вкл. |
| Целевая команда | DevOps (Ops) |
| Ключ метки | `team` |
| Значение метки | `devops` |
| Приоритет | `100` |

В списке появится `DevOps (Ops)` только после галочки. Владелец
инцидента — DevOps; Jira/Slack берутся из слотов Ops. Строка правила остаётся в таблице
Platform — там вы её создали.

<a id="read"></a>

## 07 · Если не знаете имена меток

- Пришлите один реальный алерт (или **Мастер настройки** → **Отправить тестовый алерт**).
- Откройте **Алерты** → строку → метки.
- Скопируйте одну пару ключ/значение в **Добавить правило** и сохраните.
- Повторите алерт. Должен появиться инцидент.

> **Проверка**
>
> В таблице правил рабочей области есть хотя бы одна строка. Новый подходящий алерт виден в
> **Инцидентах** на целевой команде. Дальше команде нужны
> [пути эскалации](paths.md) и дежурный.
